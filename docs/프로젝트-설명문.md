# 무비로그 — 영화·드라마 리뷰 서비스

> React의 컴포넌트, 상태, 이벤트, 비동기 데이터 처리 흐름을 직접 구현한 웹 서비스입니다. 누구나 리뷰를 읽을 수 있고, 로그인한 사용자는 자신의 리뷰를 등록·수정·삭제할 수 있습니다.

## 1. 프로젝트 소개

무비로그는 감상한 영화와 드라마에 별점과 후기를 남기는 서비스입니다. 작품 제목, 구분, 별점, 리뷰 내용을 입력하고, 선택적으로 포스터 이미지 주소와 감상 날짜를 기록할 수 있습니다.

이 프로젝트의 핵심 목표는 화면을 만드는 것뿐 아니라, **사용자 이벤트 → 상태 변경 → 화면 갱신**으로 이어지는 React의 동작 방식을 이해하는 것입니다. 서버 요청은 Supabase로 처리하고, 요청 결과에 따라 로딩·에러·빈 상태·콘텐츠를 구분해 보여줍니다.

## 2. 주요 기능

| 기능 | 사용자에게 보이는 동작 |
| --- | --- |
| 리뷰 목록 | 등록된 리뷰를 최신순 카드 목록으로 표시합니다. |
| 제목 검색·별점 필터 | 입력한 제목과 선택한 별점을 동시에 적용합니다. |
| 리뷰 상세 | 선택한 리뷰의 제목, 별점, 본문 등 정보를 표시합니다. |
| 리뷰 등록 | 로그인한 사용자가 폼을 작성하고 저장합니다. |
| 리뷰 수정 | 작성자만 기존 내용을 불러와 수정할 수 있습니다. |
| 리뷰 삭제 | 작성자가 확인 창에서 동의하면 삭제하고 목록으로 이동합니다. |
| 회원가입·로그인 | Supabase Auth로 이메일·비밀번호 인증을 처리합니다. |
| 내 기록 | 로그인한 사용자의 리뷰 수, 평균 별점, 영화·드라마 개수와 리뷰 목록을 표시합니다. |

포스터는 이미지 URL 입력과 파일 첨부 두 방식을 지원합니다. 파일은 Supabase Storage에 올리고 공개 URL을 저장하므로 DB 스키마는 두 방식이 같습니다.

## 3. 페이지와 라우팅

React Router로 페이지를 전환합니다. 공통 헤더와 내비게이션은 `Layout`에 두고, 각 페이지는 그 안에 표시합니다.

| 경로 | 화면 | 접근 조건 |
| --- | --- | --- |
| `/` | 배너·실시간 통계와 최근 리뷰 4개 | 누구나 |
| `/reviews` | 리뷰 목록·검색·필터, 10개씩 페이지네이션 | 누구나 |
| `/reviews/:id` | 리뷰 상세 | 누구나 |
| `/reviews/new` | 리뷰 등록 | 로그인 필요 |
| `/reviews/:id/edit` | 리뷰 수정 | 로그인 및 작성자 확인 |
| `/profile` | 내 리뷰 통계와 목록 (10개씩 페이지네이션) | 로그인 필요 |
| `/login` | 로그인·회원가입 | 누구나 |
| `*` | 잘못된 주소 안내 | 누구나 |

**7개의 페이지 경로와 Not Found 처리**로 최소 5개 라우트 요구사항을 만족하도록 구성했습니다. Vercel에는 SPA rewrite 설정을 두어 상세 주소로 직접 접속하거나 새로고침할 때도 앱이 열리도록 했습니다.

## 4. 코드 구조와 컴포넌트 설계

```text
src/
├── pages/        페이지 구성과 화면별 동작
├── components/   입력창, 카드, 폼, 상태 안내 등 UI
├── hooks/        리뷰 조회와 비동기 상태 관리
├── contexts/     로그인 사용자 전역 상태
├── lib/          Supabase 연결, API 함수, 입력값 검증
└── __tests__/    테스트. 위 폴더 구조를 미러링
```

컴포넌트는 **여러 화면에서 반복되는가**, **독립적인 역할이 있는가**, **props로 동작이나 표시를 바꿀 수 있는가**를 기준으로 분리했습니다.

| 역할 | 대표 컴포넌트 | 사용 예 |
| --- | --- | --- |
| 입력 | `Input`, `Textarea`, `Select`, `RatingInput` | 값, 변경 함수, 오류 메시지를 props로 전달 |
| 표시 | `Badge`, `RatingStars`, `ReviewCard` | 작품 구분, 별점, 리뷰 데이터에 따라 표시 변경 |
| 공통 상태 | `Loading`, `ErrorState`, `EmptyState` | 안내 문구와 재시도 동작을 전달 |
| 사용자 동작 | `Button`, `ConfirmDialog`, `Toast` | 제출 중 상태, 삭제 확인, 처리 결과 안내 |
| 기능 조합 | `ReviewForm`, `ReviewList`, `ReviewFilterBar` | 등록·수정 폼 공유, 목록과 검색 UI 구성 |

예를 들어 `ReviewForm`은 등록과 수정 화면이 함께 사용합니다. 등록 화면에서는 빈 입력값으로 시작하고, 수정 화면에서는 서버에서 가져온 값을 `initialValues`로 전달합니다. 버튼 문구와 제출 동작도 props로 바꿉니다.

## 5. 상태를 어디에 두었는가

상태는 사용하는 범위에 맞춰 배치했습니다. 여러 화면에 필요한 로그인 정보는 전역으로 관리하고, 특정 폼 안에서만 필요한 입력값은 폼 내부에 둡니다.

| 상태 | 관리 위치 | 이유 |
| --- | --- | --- |
| 목록 데이터·로딩·에러 | `useReviews` | 목록 조회 로직을 여러 화면에서 재사용 |
| 상세 데이터·로딩·에러 | `useReviewDetail` | 라우트의 리뷰 ID에 따라 단건 조회 |
| 검색어·별점 필터 | `ReviewListPage` | 필터 UI와 목록이 함께 사용 |
| 폼 입력값·검증 오류 | `ReviewForm` | 폼 내부 입력과 검증에 사용 |
| 제출 중·제출 실패 | 등록·수정 페이지 | 서버 저장과 성공 후 이동을 페이지가 처리 |
| 삭제 확인 창 | 상세 페이지 | 상세 화면의 삭제 동작에 사용 |
| 로그인 사용자·세션 확인 중 | `AuthContext` | 헤더, 보호 라우트, 작성자 검사 등에 공통 사용 |

### props와 state의 차이

`state`는 컴포넌트가 관리하는 변경 가능한 값입니다. `props`는 부모가 자식에게 전달하는 값이나 함수입니다.

검색어는 `ReviewListPage`의 state입니다. 페이지는 검색어와 변경 함수를 `ReviewFilterBar`에 props로 전달합니다. 사용자가 입력하면 자식이 변경 함수를 호출하고, 부모의 상태가 바뀌면서 필터 결과가 다시 계산됩니다.

### 계산 가능한 값은 별도 상태로 저장하지 않기

필터 결과는 원본 리뷰 목록, 검색어, 별점으로 계산할 수 있습니다. 별도의 state로 복사하면 원본과 결과를 함께 갱신해야 하므로, `useMemo`로 계산 결과를 재사용하도록 했습니다. 내 기록 통계도 같은 원칙을 적용했습니다.

## 6. 비동기 요청과 useEffect

조회 흐름은 다음처럼 나뉩니다.

```text
페이지 → 커스텀 훅 → API 함수 → Supabase
페이지 ← 데이터·로딩·에러 상태 ← 요청 결과
```

`useReviews`는 `{ reviews, loading, error, refetch }`를 반환하고, `useReviewDetail`은 `{ review, loading, error, refetch }`를 반환합니다. 페이지는 이 상태를 받아 적절한 UI를 표시합니다. 목록과 내 기록이 함께 쓰는 `usePagination`은 배열을 10개씩 잘라 주고 페이지 번호를 URL `?page=N`에 보관합니다.

### useEffect의 실행 시점과 의존성

목록 훅은 `useCallback`으로 만든 `load` 함수를 `useEffect`에서 호출합니다. Effect의 실제 의존성은 `[load]`이고, 목록의 `load`는 빈 의존성 배열로 유지됩니다. 페이지가 마운트되면 조회하고, 재시도 버튼을 누르면 같은 함수를 `refetch`로 호출합니다.

상세 훅의 `load`는 `[id]`에 의존합니다. 라우트의 ID가 바뀌면 `load`가 바뀌고, `[load]`를 의존성으로 둔 Effect가 다시 실행되어 새 리뷰를 조회합니다.

`AuthContext`는 최초 세션을 확인하고 인증 상태 변화를 구독합니다. Effect 정리 함수에서는 구독을 해제합니다. 알림을 자동으로 닫는 타이머 역시 정리 함수에서 해제합니다.

> 개발 환경의 React StrictMode에서는 Effect의 설정과 정리가 추가로 실행될 수 있습니다. 따라서 빈 의존성 배열을 “어떤 환경에서도 반드시 한 번만 실행된다”는 뜻으로 설명하지 않습니다.

### 요청 상태에 따른 화면

| 상태 | 표시 방식 |
| --- | --- |
| 요청 중 | `Loading`으로 진행 상태 표시 |
| 요청 실패 | `ErrorState`로 오류 안내, 조회 화면에서 재시도 제공 |
| 목록이 비어 있음 | `EmptyState`로 등록된 리뷰가 없음을 안내 |
| 검색 결과가 없음 | `EmptyState`로 조건에 맞는 리뷰가 없음을 안내 |
| 조회 성공 | 목록·상세·통계 콘텐츠 표시 |

존재하지 않는 상세 데이터는 리뷰를 찾을 수 없다는 안내 또는 조회 오류로 처리합니다.

## 7. 리뷰 등록 흐름으로 보는 React 동작

1. 사용자가 리뷰 쓰기 페이지에 접속합니다. 미로그인 상태라면 로그인 화면으로 이동합니다.
2. 제목이나 내용을 입력하면 `ReviewForm`의 state가 바뀝니다.
3. 입력값과 별점이 바뀔 때 미리보기도 갱신됩니다.
4. 제출하면 제목·구분·별점·본문의 필수값을 확인합니다. 포스터 주소를 입력했다면 `http://` 또는 `https://`로 시작하는지 확인합니다.
5. 검증에 실패하면 해당 필드 근처에 오류를 표시합니다. 입력을 수정하면 해당 필드의 기존 오류 표시를 지우고, 제출 시 다시 검증합니다.
6. 검증을 통과하면 페이지에 `onSubmit(values)`로 입력값을 전달합니다.
7. 페이지가 제출 중 상태를 켜고, 로그인 사용자의 ID를 `user_id`에 넣어 Supabase에 저장합니다.
8. 저장에 성공하면 상세 페이지로 이동하고 알림을 표시합니다. 실패하면 폼에 실패 메시지를 표시합니다.

제출 중에는 버튼이 비활성화되고 진행 상태가 표시됩니다. 수정은 같은 폼을 재사용하며, 삭제는 확인 창을 거친 뒤 성공하면 목록으로 이동합니다.

## 8. 인증과 작성자 권한

**리뷰 읽기는 공개하고, 등록·수정·삭제는 로그인 사용자와 작성자에 따라 제한합니다.**

| 작업 | 허용 범위 |
| --- | --- |
| 목록·상세 조회 | 로그인 여부와 관계없이 허용 |
| 등록 | 로그인 사용자가 본인 ID로 작성 |
| 수정·삭제 | 리뷰의 `user_id`와 로그인 사용자 ID가 같은 경우 |
| 내 기록 | 로그인 사용자의 리뷰만 집계 |

`ProtectedRoute`는 세션 확인 중에는 로딩 화면을 표시합니다. 확인이 끝난 뒤 미로그인 사용자만 로그인 화면으로 보내므로, 세션 확인 전에 성급하게 이동하지 않습니다.

상세 화면에서는 작성자에게만 수정·삭제 버튼을 보여줍니다. 수정 주소에 직접 접근한 경우에도 작성자를 검사해, 다른 사용자의 리뷰라면 폼 대신 안내를 표시합니다.

실제 데이터 접근 제한은 Supabase의 **RLS(Row Level Security)** 정책이 담당합니다. 화면의 버튼 표시와 별개로, 서버에서 `auth.uid() = user_id` 조건을 확인합니다. 따라서 화면을 우회해 요청하더라도 서버의 권한 검사가 적용됩니다.

## 9. 보너스 과제 구현

| 보너스 항목 | 구현 내용 |
| --- | --- |
| 전역 상태 | `AuthContext`로 로그인 사용자와 세션 확인 상태 공유 |
| 메모이제이션 | `useMemo`로 필터·통계·Context 전달값 재사용, `useCallback`으로 조회 함수 참조 유지 |
| 인증과 보호 라우트 | Supabase Auth와 `ProtectedRoute`, 작성자 검사 적용 |

메모이제이션은 의존성이 바뀌지 않았을 때 계산 결과나 함수 참조를 재사용하는 도구입니다. 모든 리렌더링을 막는 것은 아니며, 실제 속도 개선 정도를 별도로 측정한 것은 아닙니다.

## 11. 실행과 검증

로컬 실행 방법은 다음과 같습니다. `.env.example`을 복사한 후 본인의 Supabase 설정을 입력합니다.

```bash
npm install
cp .env.example .env
npm run dev
```

테스트와 배포용 빌드는 아래 명령으로 확인할 수 있습니다.

```bash
npm test
npm run build
```

테스트 83개 통과와 빌드 성공을 확인했습니다. 배포 환경에서는 목록·상세·등록·수정·삭제·로그인·포스터 업로드가 동작하는 것을 확인했습니다.

환경변수는 로컬 `.env`와 Vercel 배포 설정에 각각 등록합니다. 프론트엔드용 공개 키를 사용하며, 서버 관리자용 secret 또는 service_role 키는 사용하지 않습니다. 브라우저에 전달되는 공개 키를 숨기는 것으로 권한을 통제할 수 없으므로 RLS 정책이 필요합니다.

## 12. 발표·시연 순서

1. 로그아웃 상태에서 목록과 상세가 공개되어 있음을 보여줍니다.
2. 제목 검색과 별점 필터를 바꿔 목록과 개수가 갱신되는 모습을 보여줍니다.
3. 리뷰 쓰기에 접근하면 로그인 화면으로 이동하는 것을 보여줍니다.
4. 로그인 후 새 리뷰를 작성하며 필수값 검증과 실시간 미리보기를 보여줍니다.
5. 저장 후 상세로 이동하고 수정·삭제 버튼이 표시되는 것을 보여줍니다.
6. 리뷰를 수정하고 내 기록 통계에 반영되는지 확인합니다.
7. 시연용 리뷰를 삭제하고 목록으로 돌아오는 것을 보여줍니다.
8. 상세 주소 직접 접속과 잘못된 주소 안내를 보여줍니다.

기존 샘플 리뷰도 본인 계정으로 이전했다면 해당 리뷰는 모두 수정·삭제할 수 있습니다. 다른 작성자의 리뷰에 대한 권한 제한을 시연하려면 별도 계정의 리뷰가 필요합니다. 기존 리뷰 대신 삭제해도 되는 시연용 리뷰로 CRUD를 보여주는 것이 좋습니다.

## 13. 발표용 설명 예시

무비로그는 영화와 드라마의 감상을 기록하는 React 기반 SPA입니다. Supabase로 리뷰 데이터를 저장하고, 로그인한 사용자만 자신의 리뷰를 등록·수정·삭제할 수 있도록 만들었습니다.

컴포넌트는 역할과 재사용 여부를 기준으로 나눴습니다. 등록과 수정은 같은 ReviewForm을 사용하고, 로딩·오류·빈 상태도 공통 컴포넌트로 처리합니다.

상태는 필요한 범위에 맞춰 배치했습니다. 서버 데이터는 커스텀 훅, 검색 조건과 제출 상태는 페이지, 입력값은 폼 내부에서 관리합니다. 여러 화면에서 사용하는 로그인 정보는 Context로 공유합니다.

입력이나 클릭이 상태를 바꾸면 미리보기, 목록, 버튼 상태가 달라집니다. 이를 통해 사용자 이벤트가 React 렌더링으로 이어지는 흐름을 구현했습니다. 권한은 화면에서 작성자를 확인하고, Supabase RLS에서도 검사하도록 구성했습니다.
