## 1. 기능 동작 검증

### Q1. 최소 5개 이상의 라우트가 동작하고, 잘못된 주소 접근 시 Not Found 페이지가 표시되는가?

**답변**

React Router로 7개의 페이지 경로를 구성했습니다. 여기에 일치하는 경로가 없을 때 처리하는 `*` 경로를 추가했습니다.

| 경로 | 화면 | 접근 조건 |
| --- | --- | --- |
| `/` | 홈, 전체 통계와 최근 리뷰 최대 4개 | 공개 |
| `/reviews` | 목록, 검색, 별점 필터, 페이지네이션 | 공개 |
| `/reviews/:id` | 리뷰 상세 | 공개 |
| `/reviews/new` | 리뷰 등록 | 로그인 필요 |
| `/reviews/:id/edit` | 리뷰 수정 | 로그인 및 작성자 확인 |
| `/login` | 로그인·회원가입 | 공개 |
| `/profile` | 내 리뷰 통계와 목록 | 로그인 필요 |
| `*` | Not Found | 잘못된 주소 처리 |

등록·수정·내 기록은 `ProtectedRoute`로 묶었습니다. 공통 `Layout`이 헤더와 내비게이션을 제공하고, 자식 경로의 화면을 표시합니다.

**코드 근거:** [App.jsx](../src/App.jsx), [ProtectedRoute.jsx](../src/components/ProtectedRoute.jsx), [NotFoundPage.jsx](../src/pages/NotFoundPage.jsx)

**시연:** 주요 메뉴를 이동한 다음 `/unknown`에 접속해 Not Found를 보여줍니다.

### Q2. 목록 조회, 상세 조회, 등록, 수정, 삭제가 모두 정상 동작하는가?

**답변**

CRUD는 Supabase의 `reviews` 테이블에 연결했습니다. 목록 조회는 `fetchReviews`, 단건 조회는 `fetchReviewById`, 등록은 `createReview`, 수정은 `updateReview`, 삭제는 `deleteReview`가 담당합니다.

목록은 생성일 내림차순으로 조회합니다. 상세는 URL의 `id`로 특정 리뷰를 조회합니다. 등록 시에는 로그인 사용자의 ID를 `user_id`에 함께 저장합니다.

등록·수정에 성공하면 상세 페이지로 이동하고 알림을 표시합니다. 삭제는 확인 창을 거친 뒤 성공하면 목록으로 이동하며, 목록 화면이 데이터를 다시 조회합니다. 수정·삭제 버튼은 작성자에게만 보이고, 수정 주소에 직접 접근해도 작성자를 검사합니다.

이 흐름의 구현과 관련 자동 테스트를 확인했습니다. 실제 배포 환경의 정상 동작은 로그인한 상태에서 CRUD를 시연해 최종 확인해야 합니다.

**코드 근거:** [reviewsApi.js](../src/lib/reviewsApi.js), [ReviewNewPage.jsx](../src/pages/ReviewNewPage.jsx), [ReviewEditPage.jsx](../src/pages/ReviewEditPage.jsx), [ReviewDetailPage.jsx](../src/pages/ReviewDetailPage.jsx)

**시연:** 테스트용 리뷰 등록 → 상세 조회 → 내용·별점 수정 → 삭제 확인 → 목록 복귀 순으로 보여줍니다.

### Q3. 로딩·에러·빈 상태가 핵심 화면에서 일관되게 표시되는가?

**답변**

데이터 조회 화면에서는 `Loading`, `ErrorState`, `EmptyState`를 공통으로 사용합니다. 요청 중인지, 오류가 있는지, 데이터가 비어 있는지 순서대로 확인합니다.

목록은 “등록된 리뷰가 없음”과 “검색 조건에 맞는 결과가 없음”을 구분합니다. 내 기록은 내가 작성한 리뷰가 없다는 안내를 표시합니다. 상세·수정 화면에서 데이터가 없거나 조회에 실패하면 오류 안내를 표시합니다.

등록 화면은 최초 조회가 필요하지 않으므로 목록과 같은 빈 상태 분기를 두지 않습니다. 대신 입력 오류와 저장 중·실패 상태를 처리합니다. 모든 화면에 동일한 네 가지 상태를 억지로 넣기보다, 해당 화면에 필요한 상태를 공통 패턴으로 처리했습니다.

**코드 근거:** [ReviewListPage.jsx](../src/pages/ReviewListPage.jsx)의 `renderBody`, [HomePage.jsx](../src/pages/HomePage.jsx)의 `renderRecent`, [ProfilePage.jsx](../src/pages/ProfilePage.jsx)

### Q4. 폼의 필수값 검증, 에러 메시지, 제출 중 표시가 동작하는가?

**답변**

`ReviewForm`에서 제출 전에 `validateReview`를 호출합니다. 제목과 본문은 공백만 입력한 경우도 막고, 구분·별점의 필수값을 확인합니다. 포스터 URL은 입력한 경우 `http://` 또는 `https://`로 시작하는지 검사합니다. URL 전체의 유효성을 완전히 검증하는 방식은 아닙니다.

검증 오류는 필드 근처에 표시합니다. 입력을 수정하면 해당 필드의 기존 오류만 지우고, 제출할 때 다시 검증합니다.

저장 요청 중에는 `submitting`을 `Button`의 `loading` prop으로 전달해 버튼을 비활성화하고 스피너와 “처리 중...” 문구를 표시합니다. 실패하면 폼 상단에 메시지를 표시합니다.

추가로 수정 폼은 초기값과 달라진 내용이 없으면 저장 버튼을 비활성화합니다. 포스터 파일은 이미지 형식과 2MB 이하 크기를 확인하며, 업로드 중에도 저장 버튼을 비활성화합니다. 파일 선택 자체는 브라우저의 파일 입력을 사용하고, 업로드 결과 URL과 진행 상태를 React로 관리합니다.

**코드 근거:** [ReviewForm.jsx](../src/components/ReviewForm.jsx)의 `handleSubmit`, `setField`, `isDirty`, [validation.js](../src/lib/validation.js), [Button.jsx](../src/components/Button.jsx), [storageApi.js](../src/lib/storageApi.js)

### Q5. 배포된 URL에서 CRUD를 포함한 모든 기능이 정상 동작하는가?

**답변**

Vercel 배포와 Supabase 연결을 구성했고, 이전 작업에서는 배포본의 CRUD와 상세 주소 직접 접속을 확인했습니다. `vercel.json`에는 SPA 경로를 `index.html`로 연결하는 rewrite 설정이 있습니다.

이번 재분석에서는 현재 코드의 자동 테스트 83개와 빌드가 통과했습니다. 다만 이것만으로 최신 배포본의 모든 기능이 정상이라고 확정할 수는 없습니다. 현재 추가된 포스터 업로드는 실제 Storage 버킷과 정책 설정에도 의존하므로, 로그인 후 CRUD·업로드·직접 주소 접속을 시연해야 최종 확인할 수 있습니다.

**코드 근거:** [vercel.json](../vercel.json), [supabaseClient.js](../src/lib/supabaseClient.js), [storageApi.js](../src/lib/storageApi.js)

**배포본 확인 목록**

- [ ] 로그인하지 않아도 목록·상세를 조회할 수 있다.
- [ ] 로그인 후 본인 리뷰를 등록·수정·삭제할 수 있다.
- [ ] 포스터 URL 입력과 파일 업로드가 동작한다.
- [ ] 상세·수정 주소에서 새로고침해도 앱이 열린다.
- [ ] 다른 사용자의 리뷰 수정은 제한된다.

## 2. 코드 구조 및 설계

### Q6. 조회·갱신 흐름이 커스텀 훅으로 분리되어 있으며, 이유를 설명할 수 있는가?

**답변**

목록 조회는 `useReviews`, 상세 조회는 `useReviewDetail`로 분리했습니다. 데이터뿐 아니라 로딩, 오류, 재조회 함수까지 훅이 관리합니다.

페이지마다 요청 시작·성공·실패·종료 코드를 반복하지 않고, 데이터 처리와 화면 구성을 나누기 위해서입니다. `useReviews`는 홈·목록·내 기록에서, `useReviewDetail`은 상세·수정 화면에서 재사용합니다.

반환값은 각각 `{ reviews, loading, error, refetch }`와 `{ review, loading, error, refetch }`입니다. 훅 호출마다 상태는 독립적이며, 같은 훅을 사용한다고 서버 데이터나 캐시가 전역으로 공유되는 것은 아닙니다. 등록·수정·삭제 요청은 페이지의 이벤트 처리 함수에서 API 함수를 호출합니다.

**코드 근거:** [useReviews.js](../src/hooks/useReviews.js), [useReviewDetail.js](../src/hooks/useReviewDetail.js)

### Q7. pages, components, hooks·lib로 나눈 이유는 무엇인가?

**답변**

변경할 기능의 위치를 쉽게 찾고 역할을 구분하기 위해 분리했습니다.

| 폴더 | 역할 | 예시 |
| --- | --- | --- |
| `pages` | 경로별 화면 조합, 제출 처리와 이동 | `ReviewNewPage` |
| `components` | props로 동작·표시를 바꾸는 UI | `ReviewForm`, `ReviewCard` |
| `hooks` | React 상태를 사용하는 공통 로직 | `useReviews`, `usePagination` |
| `lib` | 통신, 검증, 외부 서비스 연결 | `reviewsApi`, `validation` |
| `contexts` | 여러 화면이 사용하는 전역 상태 | `AuthContext` |
| `__tests__` | 페이지·훅·컴포넌트·API 테스트 | 기능별 하위 폴더 |

예를 들어 조회 조건은 API 함수에서, 로딩 상태 처리는 훅에서, 카드 디자인은 컴포넌트에서 바꿀 수 있습니다. 홈의 `HeroBanner`, 내 기록의 `StatCard`처럼 해당 화면 안에서만 사용하는 작은 컴포넌트는 페이지 파일에 함께 두었습니다.

### Q8. 재사용 컴포넌트가 8개 이상이며, 나눈 기준을 구체적으로 말할 수 있는가?

**답변**

단순히 파일 수로 판단하지 않고, props에 따라 표시나 동작이 달라지는 컴포넌트를 기준으로 설명할 수 있습니다.

### Q9. 로딩·에러·빈 상태 UI가 공통 컴포넌트로 통일되어 있는가?

**답변**

조회 상태 UI는 `Loading`, `ErrorState`, `EmptyState`로 통일했습니다. 페이지는 상태를 판단하고, 실제 표시는 공통 컴포넌트에 맡깁니다.

예를 들어 목록은 오류가 있으면 `ErrorState`에 오류 메시지와 `refetch`를 전달합니다. 홈과 내 기록도 같은 컴포넌트를 사용하므로 안내 모양이나 재시도 버튼을 한곳에서 관리할 수 있습니다.

단, 모든 오류 UI가 하나로 통합된 것은 아닙니다. 입력 오류는 각 입력 컴포넌트에서, 저장 실패는 폼 상단에서, 삭제 실패는 상세 화면의 배너에서 표시합니다. 조회 상태 공통화와 입력·작업 오류 처리를 구분해서 설명하는 것이 정확합니다.

**코드 근거:** [Loading.jsx](../src/components/Loading.jsx), [ErrorState.jsx](../src/components/ErrorState.jsx), [EmptyState.jsx](../src/components/EmptyState.jsx), [ReviewListPage.jsx](../src/pages/ReviewListPage.jsx)

### Q10. 훅으로 분리한 데이터 흐름 하나와 그 이유를 말할 수 있는가?

**답변**

상세 조회를 예로 들면 다음과 같습니다.

```text
URL의 리뷰 ID
  → 페이지의 useParams()
  → useReviewDetail(id)
  → fetchReviewById(id)
  → Supabase 단건 조회
  → review / loading / error 상태 변경
  → 상세 내용 또는 수정 폼 표시
```

상세 페이지와 수정 페이지가 같은 데이터를 조회하기 때문에 훅으로 분리했습니다. 각 페이지는 요청 상태 관리 코드를 다시 작성하지 않고, 조회한 리뷰를 표시하거나 폼 초기값으로 사용할 수 있습니다.

추가로 `usePagination`은 목록을 페이지별로 나누는 로직과 URL의 페이지 번호를 관리합니다. 리뷰 목록과 내 기록 목록에 같은 로직을 적용합니다.

**코드 근거:** [useReviewDetail.js](../src/hooks/useReviewDetail.js), [ReviewEditPage.jsx](../src/pages/ReviewEditPage.jsx), [usePagination.js](../src/hooks/usePagination.js)

## 3. 핵심 기술 원리 적용

### Q11. props와 state를 구분하고 상태 배치 흐름을 설명할 수 있는가?

**답변**

`state`는 컴포넌트가 관리하는 변경 가능한 값이고, `props`는 부모가 자식에게 전달하는 값이나 함수입니다. 자식은 받은 props를 직접 수정하지 않고 전달받은 함수를 호출해 변경을 요청합니다.

검색어와 별점 필터는 `ReviewListPage`의 state입니다. 이를 `ReviewFilterBar`에 props로 전달합니다. 사용자가 입력하면 자식이 변경 함수를 호출하고, 부모 상태가 바뀌면서 목록이 갱신됩니다.

폼 입력값은 폼 내부에서만 사용하므로 `ReviewForm`이 관리합니다. 제출 시 `onSubmit(values)`로 페이지에 전달합니다. 서버 데이터는 조회 훅이 관리하고, 헤더·보호 라우트·작성자 검사에 함께 필요한 로그인 정보는 `AuthContext`가 관리합니다.

| 상태 | 위치 |
| --- | --- |
| 리뷰·로딩·조회 오류 | 조회 커스텀 훅 |
| 검색어·별점 조건 | 목록 페이지 |
| 입력값·검증 오류·업로드 상태 | 리뷰 폼 |
| 제출 중·제출 실패 | 등록·수정 페이지 |
| 삭제 확인 창·삭제 중 | 상세 페이지 |
| 사용자·세션 확인 중 | AuthContext |
| 페이지 번호 | URL 검색 매개변수 `?page=N` |

페이지 번호를 URL에 두면 새로고침·뒤로가기에 반영됩니다. 검색어와 별점은 현재 지역 state이므로 같은 방식으로 URL에 보존되는 것은 아닙니다.

### Q12. useEffect의 실행 시점과 의존성 배열을 코드 기준으로 설명할 수 있는가?

**답변**

`useEffect`는 렌더링 결과가 반영된 뒤 데이터 요청이나 구독 같은 외부 작업을 실행하는 데 사용했습니다. 의존성 배열에 있는 값이 이전과 달라지면 Effect가 다시 실행됩니다.

목록 훅에서는 `load`를 `useCallback`으로 만들고 Effect의 의존성을 `[load]`로 설정합니다. 목록의 `load`는 빈 의존성 배열을 사용해 일반적인 리렌더링 사이에서 참조가 유지됩니다.

상세 훅의 `load`는 `[id]`에 의존합니다. ID가 바뀌면 함수 참조가 바뀌고 `[load]`에 의존하는 Effect가 다시 조회합니다. 따라서 **실제 Effect의 의존성은 `[load]`, 조회 함수의 의존성은 `[id]`**입니다.

`AuthContext`에서는 세션을 읽고 인증 변화를 구독하며, 정리 함수에서 구독을 해제합니다. 토스트를 닫는 타이머도 정리 함수에서 해제합니다.

개발 환경의 StrictMode에서는 Effect 설정·정리가 추가 실행될 수 있습니다. 빈 배열을 “모든 상황에서 반드시 한 번만 실행된다”는 뜻으로 설명하지 않습니다. 또한 `useCallback`은 함수를 실행하는 기능이 아니라 함수 참조를 재사용하는 기능입니다.

**코드 근거:** [useReviews.js](../src/hooks/useReviews.js), [useReviewDetail.js](../src/hooks/useReviewDetail.js), [AuthContext.jsx](../src/contexts/AuthContext.jsx), [main.jsx](../src/main.jsx)

### Q13. 비동기 요청의 로딩·성공·실패·빈 상태를 어떻게 처리했는가?

**답변**

요청 전에 `loading`을 true로 설정하고 이전 `error`를 지웁니다. 성공하면 데이터를 저장하고, 실패하면 오류 메시지를 저장합니다. `finally`에서는 성공 여부와 관계없이 로딩을 종료합니다.

페이지는 다음 순서로 화면을 결정합니다.

| 조건 | 렌더링 |
| --- | --- |
| 요청 중 | Loading |
| 오류 있음 | ErrorState와 조회 재시도 |
| 요청 성공, 데이터 없음 | EmptyState |
| 요청 성공, 데이터 있음 | 리뷰 목록·상세·통계 |

성공을 별도 `success` state로 저장하지는 않습니다. 요청이 끝났고 오류가 없는지로 판단합니다. 오류 검사를 빈 데이터 검사보다 먼저 하기 때문에, 실패로 목록이 비워져도 “등록된 리뷰가 없다”고 잘못 안내하지 않습니다.

**코드 근거:** [useReviews.js](../src/hooks/useReviews.js)의 `load`, [ReviewListPage.jsx](../src/pages/ReviewListPage.jsx)의 `renderBody`

### Q14. 상태 변경이 화면 변화로 이어지는 지점을 3군데 이상 설명할 수 있는가?

**답변**

| 사용자 이벤트 | 바뀌는 값 | 화면 변화 | 코드 위치 |
| --- | --- | --- | --- |
| 제목 검색·별점 선택 | `keyword`, `rating` | 필터 목록·개수 갱신, 첫 페이지로 이동 | ReviewListPage |
| 제목·구분·별점 입력 | `values` | 미리보기 갱신 | ReviewForm |
| 등록·수정 제출 | `submitting` | 버튼 비활성화·진행 표시 | ReviewNewPage, ReviewEditPage, Button |
| 수정 폼 내용 변경 | `values`에서 파생한 `isDirty` | 변경이 있으면 저장 버튼 활성화 | ReviewForm |
| 삭제 버튼 클릭 | `confirmOpen` | 확인 창 표시 | ReviewDetailPage |
| 파일 선택·업로드 완료 | `uploading`, `poster_url` | 업로드 안내·포스터 미리보기 | ReviewForm |
| 페이지 이동 | URL의 `page` | 표시할 리뷰 10개 조각 변경 | usePagination |

필터 결과와 `isDirty`는 별도의 state로 복사하지 않고 기존 상태에서 계산하는 값입니다. `useMemo`는 의존성이 같을 때 계산 결과를 재사용하며, 컴포넌트의 모든 리렌더링을 막지는 않습니다.

### Q15. 라우팅 → 컴포넌트 → 상태 → 이벤트 → 렌더링의 연결을 설명할 수 있는가?

**답변 — 리뷰 등록 사례**

1. 사용자가 `/reviews/new`에 접속합니다. 라우터는 `ProtectedRoute`를 거쳐 로그인 여부를 확인합니다.
2. 로그인 상태라면 `ReviewNewPage`가 `ReviewForm`을 표시합니다.
3. 입력 이벤트가 발생하면 폼의 `values` 상태가 바뀌고 입력창·미리보기가 갱신됩니다.
4. 제출 이벤트에서는 검증을 실행합니다. 오류가 있으면 `errors`를 바꿔 필드별 안내를 표시합니다.
5. 통과하면 `onSubmit(values)`로 부모 페이지에 값을 전달합니다.
6. 페이지는 `submitting`을 켜고 사용자 ID를 포함해 `createReview`를 호출합니다. 버튼이 진행 중 상태로 바뀝니다.
7. 저장에 성공하면 생성된 ID의 상세 주소로 이동합니다. 상세 페이지가 리뷰를 조회하고 등록 완료 알림을 표시합니다.
8. 실패하면 현재 폼에 실패 메시지를 표시하고 제출 중 상태를 종료합니다.

이 흐름에서 폼은 입력·검증을, 페이지는 저장·이동을, API 함수는 Supabase 통신을 담당합니다.

### Q16. Supabase를 선택한 이유와 연동하면서 겪은 어려움은 무엇인가?

**답변**

과제의 중심이 React이므로 별도의 백엔드 서버를 구축하지 않고 데이터 저장과 인증을 연결할 수 있는 Supabase를 선택했습니다. PostgreSQL 테이블로 리뷰 필드를 명확하게 정의하고 JavaScript SDK로 CRUD를 호출할 수 있다는 점도 적합했습니다. 현재는 포스터 저장에 Storage도 사용합니다.

연동 중에는 다음 문제를 겪었습니다.

**첫째, 대시보드 URL과 API URL을 혼동했습니다.** 브라우저에서 보는 대시보드 주소를 연결 주소로 넣어 요청이 실패했습니다. 프로젝트 API 주소로 수정했고, 로컬뿐 아니라 Vercel 환경변수도 수정한 뒤 재배포해야 했습니다.

**둘째, 인증 도입 시 데이터 소유권도 함께 설계해야 했습니다.** 리뷰에 `user_id`를 추가하고 등록 시 로그인 사용자 ID를 저장했습니다. 읽기는 공개하고 쓰기는 본인 데이터에 한정하도록 RLS 정책을 설정했습니다. 기존 샘플에는 작성자가 없어 별도로 계정에 연결했습니다.

**셋째, 로그인 검사와 작성자 검사는 다른 문제였습니다.** 로그인만 확인하면 다른 사람의 수정 주소에서 폼을 볼 수 있었습니다. 수정 페이지에 작성자 검사를 추가했고, 실제 데이터 변경은 서버의 RLS로 제한하도록 구성했습니다.

이 경험으로 화면의 접근 제어, 서버의 데이터 권한, 배포 환경변수를 각각 확인해야 한다는 점을 배웠습니다. 프론트엔드에서 버튼을 숨기는 것만으로 데이터 권한이 보장되지는 않습니다.

**코드 근거:** [supabaseClient.js](../src/lib/supabaseClient.js), [ReviewNewPage.jsx](../src/pages/ReviewNewPage.jsx), [ReviewEditPage.jsx](../src/pages/ReviewEditPage.jsx), [README의 테이블·정책 설명](../README.md)

## 6. 현재 한계와 개선 방향

면담에서는 구현 범위와 한계를 함께 설명하는 것이 정확합니다. 다음은 코드에서 확인한 개선 가능 지점이며, 이 문서 작성 과정에서 코드를 수정하지는 않았습니다.

- **요청 순서 제어:** 조회 훅에 요청 취소나 오래된 응답 무시 처리가 없습니다. 빠르게 다른 리뷰로 이동할 때 이전 요청 결과가 뒤늦게 반영되지 않도록 보완할 수 있습니다.
- **클라이언트 페이지네이션:** 서버가 반환한 목록을 브라우저에서 10개씩 자릅니다. 서버에서 10개씩 조회하는 구조가 아니므로 데이터가 늘면 검색·필터·페이지네이션을 서버 쪽으로 옮길 수 있습니다.
- **페이지 번호 검증:** URL의 페이지 번호가 전체 페이지 수를 초과하면 보정하지만, 음수·소수 입력을 양의 정수로 정규화하는 처리는 부족합니다.
- **삭제 결과 확인:** 삭제 API는 오류 유무를 확인하지만 실제 삭제 행 수는 확인하지 않습니다. 권한 때문에 0건 처리된 경우까지 명확히 구분하도록 개선할 수 있습니다.
- **오류 UI 공통화 범위:** 조회 상태 UI는 공통화했지만 폼·삭제 실패 배너는 일부 별도로 구현되어 있습니다.
- **배포 검증:** 자동 테스트는 실제 Supabase 권한·Storage 설정·사용자 브라우저 동작 전체를 대신하지 않습니다. 제출 전에 배포본을 시연해야 합니다.

## 7. 평가 시연 순서

1. 로그아웃 상태에서 목록·상세 공개 조회를 보여줍니다.
2. 검색·별점 필터와 페이지네이션을 보여줍니다.
3. 리뷰 쓰기에 접속해 로그인 화면으로 이동하는 것을 보여줍니다.
4. 로그인 후 빈 폼 제출로 검증 메시지를 보여줍니다.
5. 입력·미리보기·포스터 업로드 후 테스트용 리뷰를 등록합니다.
6. 상세 주소에서 새로고침하고 수정 화면으로 이동합니다.
7. 수정 전에는 버튼이 비활성화되고 값을 바꾸면 활성화되는 것을 보여줍니다.
8. 저장 결과와 내 기록 통계·목록을 확인합니다.
9. 테스트용 리뷰를 삭제하고 목록 복귀를 확인합니다.
10. 잘못된 주소에서 Not Found를 보여줍니다.

기존 샘플을 본인 계정으로 이전했다면 해당 리뷰는 본인 데이터입니다. 다른 작성자의 리뷰에 대한 제한을 시연하려면 별도 계정의 리뷰가 필요합니다. 실제 사용 중인 리뷰 대신 삭제해도 되는 시연용 리뷰로 검증합니다.
